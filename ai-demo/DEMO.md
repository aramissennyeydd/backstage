# Catalog-scoped skills demo

> This demo is not intended for upstream merge. It lives on a demo branch based on `sennyeya/cli-module-ai` and exists to show the `ai` CLI module end to end.

Everything runs from this checkout. `ai-demo/` is the demo directory (`$DEMO`) and the repo root is the checkout with the module (`$WT`). Neither is hard coded, `setup.sh` and `env.sh` derive them from their own location.

## Story

Two teams, one prompt. The payments team and the growth team both ask a coding agent to "add a refund function and tests, following this project's conventions". Neither repo contains any agent instructions. Each repo's session start hook asks the Backstage catalog which skills apply to the component behind the git remote, installs exactly those, and the agent writes code that matches its team. Payments gets injected clients, typed errors, idempotency keys, bounded retries and builder-based multi-assertion tests. Growth gets a plain function and table-driven `it.each` tests. A third repo with no skills gets nothing built at all, only questions, because it has no conventions to follow.

## Catalog setup

Skills are plain directories (`team-skills/skills/<name>/SKILL.md`) referenced as `backstage.io/source-location: file:<abs path>`. File sources are opt-in, so every CLI command in this demo passes `--allow-file-sources`. Catalog file: `backend-config/catalog-demo.yaml`, generated by `setup.sh` from `backend-config/catalog-demo.template.yaml` so the `file:` paths match where this checkout lives.

Groups: `engineering` (root) with children `platform`, `payments`, `growth`. `demo-user` is `memberOf: [engineering]` only (with one login, membership in both teams would make every team skill match both repos, so team scoping comes from the component owner, the system and ancestor groups). Systems: `checkout` (payments), `marketing` (growth). Components: `payments-service` (owner payments, system checkout) and `growth-service` (owner growth, system marketing), matched by `github.com/project-slug` and the git remote.

| Skill                        | Owner       | System   | `dependsOn`        | Reaches                               |
| ---------------------------- | ----------- | -------- | ------------------ | ------------------------------------- |
| commenting-standards         | engineering | -        | -                  | both (ancestor group of the owners)   |
| payments-code-shape          | payments    | -        | -                  | payments-service                      |
| payments-testing             | payments    | -        | -                  | payments-service                      |
| growth-testing               | growth      | -        | -                  | growth-service                        |
| payments-gateway-integration | payments    | checkout | api-error-handling | payments-service (system)             |
| api-error-handling           | platform    | -        | -                  | payments-service only via `dependsOn` |

Note: `ai resolve` shows "User groups: -" because the guest login's ownership claim contains only the user ref. Membership in `engineering` is not what drives selection here, the component owner's ancestors are.

Expected skills per repo:

- `repo/` (payments-service): api-error-handling, commenting-standards, payments-code-shape, payments-gateway-integration, payments-testing.
- `growth-repo/` (growth-service): commenting-standards, growth-testing.
- `baseline-repo/` (origin is also payments-service, but it is run without hooks): none.

Repo remotes: `repo` and `baseline-repo` use `https://github.com/acme-demo/payments-service.git`, `growth-repo` uses `https://github.com/acme-demo/growth-service.git`. Each repo has `node_modules/@backstage/cli-module-ai` and `cli-module-auth` symlinked to this checkout's `packages/cli-module-ai` and `packages/cli-module-auth`.

## What is committed

- `templates/repo`, `templates/growth-repo`, `templates/baseline-repo`: starter code for the three demo repos.
- `templates/team-skills`: the six skills.
- `backend-config/*.template.yaml`: catalog and app config with a `@@DEMO@@` placeholder.
- `env.sh`, `setup.sh`, `run-comparison.sh`.

`setup.sh` generates the working copies (ignored by git): `repo/`, `growth-repo/`, `baseline-repo/` (each a fresh `git init` with a "starting point" commit and its `origin`), `team-skills/` (a local git repo), the `node_modules/@backstage` symlinks, and `backend-config/catalog-demo.yaml` and `app-config.demo.yaml`. `results/`, `logs/`, `xdg-config/` and `xdg-data/` are created while running and are ignored by git too.

## Run it

Run `yarn install` in the repo root first if you have not (needed by `yarn start`). Then, from the repo root:

```bash
D=$PWD/ai-demo
```

### 0. Set up

```bash
bash $D/setup.sh
```

Re-running it recreates the demo repos from scratch.

### 1. Terminal A: backend on :7107

Guest auth, refresh tokens and the demo catalog. The database is in memory, so every restart needs a new login (step 4).

```bash
cd packages/backend
yarn start --config ../../app-config.yaml --config $D/backend-config/app-config.demo.yaml
```

### 2. Terminal B: frontend on :3100

Needed for the CLI login consent page. `BROWSER=none` stops the dev server from opening a browser tab, since login opens its own page.

```bash
cd packages/app
BROWSER=none yarn start --config ../../app-config.yaml --config $D/backend-config/app-config.demo.yaml
```

### 2.5. Optional: start everything with `herdr`

From inside a `herdr` session, after `setup.sh`, run:

```bash
bash ai-demo/herdr.sh
```

The script first stops anything listening on ports 7107 and 3100 (SIGTERM, then SIGKILL if the port stays busy) and prints what it stopped. It then opens an `ai-demo` tab with the backend (top left), the frontend (bottom left), and a full-height demo shell (right). The shell waits for both servers, then sources `env.sh` and starts `backstage-cli auth login`. After approving the consent page, continue from the resolve step (step 5). Requires `jq` and `lsof`.

### 3. Terminal C: load the helpers

Defines `ai`, `auth` and `backstage-cli` helpers, sets `BACKEND_URL=http://localhost:7107`, and puts the login state in `$DEMO/xdg-config` and `$DEMO/xdg-data`. It also sets `WT` and `DEMO`.

```bash
source ai-demo/env.sh
D=$DEMO
```

### 4. Log in (browser consent, once per backend start)

```bash
backstage-cli auth login --backend-url http://localhost:7107 --instance ai-demo
```

### 5. Check which skills apply

```bash
cd $D/repo
backstage-cli ai resolve --allow-file-sources --instance ai-demo --agent claude-code
backstage-cli ai resolve --allow-file-sources --instance ai-demo --output json   # machine-readable
cd $D/growth-repo
backstage-cli ai resolve --allow-file-sources --instance ai-demo --agent claude-code
```

`--entity <ref>` skips git remote detection. `--agent` is repeatable; without it the agent is detected.

### 6. Install the session start hook

```bash
cd $D/repo
backstage-cli ai hooks install --allow-file-sources --instance ai-demo --agent claude-code --agent codex
```

`--agent` is required and repeatable. `--dry-run` prints the hook files without writing them. The hook runs `ai skills sync --hook`, which never fails or prompts and skips installed skills.

### 7. Or sync the skills directly

```bash
backstage-cli ai skills sync --allow-file-sources --instance ai-demo --agent claude-code --agent codex
```

Other flags: `--dry-run` (print the skills commands only), `--global` (user-level skills directories), `--entity`.

### 8. Codex hook approval

Codex does not run a project hook until you approve it. Start `codex` in the repo and run `/hooks`, then approve the Backstage session start hook. Start a new session afterwards and the skills are installed under `.agents/skills`.

### 9. Run the comparison

```bash
bash $D/run-comparison.sh
```

Resets each repo to its committed starting point, then for payments and growth runs `ai resolve`, `ai hooks install --agent claude-code`, a headless `claude -p "Reply with OK."` so the hook installs the skills, and then the refund prompt. The baseline gets the prompt without skills. Output lands in `$D/results` (`<name>.resolve.txt`, `.resolve.json`, `.skills.txt`, `.claude.txt`, `.diff`, `.src/`). Requires `claude` on the PATH.

The script runs every `claude` call with `--setting-sources project,local --strict-mcp-config` (and no MCP config), so only the project settings load and no MCP servers run. Your user-level plugins, hooks and servers stay out, and the comparison isolates the skills. Managed organization settings still apply.

## The prompt (identical in all three repos)

> Add a function in src/refunds.ts that issues a refund for a payment through our Payments Gateway, and add tests for it in src/refunds.test.ts. Follow this project's conventions.

Run with `--permission-mode acceptEdits --allowedTools "Read,Write,Edit,Glob,Grep" --max-turns 15` (no Bash, so nothing is executed or installed).

## Manual version of one repo

```bash
cd $D/repo
backstage-cli ai hooks install --agent claude-code --allow-file-sources --instance ai-demo
claude -p "Reply with OK." --max-turns 1          # SessionStart hook installs .claude/skills
ls .claude/skills
claude -p "Add a function in src/refunds.ts that issues a refund for a payment through our Payments Gateway, and add tests for it in src/refunds.test.ts. Follow this project's conventions." \
  --permission-mode acceptEdits --allowedTools "Read,Write,Edit,Glob,Grep" --max-turns 15
# repeat in $D/growth-repo and $D/baseline-repo (skip resolve/hooks for the baseline)
```

## What a previous run showed

Models are nondeterministic, so a re-run produces different code, but the pattern was stable.

- Payments (5 skills): injected `GatewayClient`, explicit return types, an idempotency key generated once outside the retry loop, retries only on 429 and 503 with a max of 3 attempts, typed errors (`UpstreamError`, `PaymentNotFoundError`, `RefundExceedsCaptureError`), TSDoc on exports, and tests with builders, a fake gateway at the HTTP boundary and behavior-named multi-assertion cases.
- Growth (2 skills): no gateway skill, so the agent invented a `PaymentsGateway.refund()` interface with plain `Error`s, but TSDoc from the shared commenting-standards skill and `it.each` tables from growth-testing.
- Baseline (no skills): wrote no code. It found no gateway client, URL, test runner or conventions and replied with questions.

Honest notes: payments had one `catch { return undefined; }` that brushes against api-error-handling, and growth mixed `it.each` with a few standalone cases. Neither repo has a test runner, so tests are never run.
